# Executive Verdict

ARgentOS today is a **coherent, unusually well-governed specification framework — not an
operationally deterministic, mechanically enforceable system.** The architecture is real and
mostly self-consistent at the *documental* level: the state machines, contracts, policies, and
governance apparatus form a genuine declarative model, and the development-side verification
battery is substantive. But the product's own core guarantees are **declared, not enforced**:

- The harness is explicitly a **self-assessment**: "There is no executable validation runner";
  every gate policy says the Orchestrator evaluates the checklist **by judgment**, and the audit
  trail (`HARNESS_REPORT.md`) is **written by the same Orchestrator** that makes the decision.
- Every context-resolution, composition, tie-breaking, merge, deduplication, and budget rule is
  marked `[agent]` judgment, with machine checks explicitly deferred to "harness Future
  Extension".
- "Zero hallucination" has no deterministic mechanism behind it; D01's ground-truth gate is
  `[agent]`, and the anti-hallucination skill is a prompt.
- There are **live internal contradictions** in the canonical payload: the taxonomy's `RECOVERY`
  transition set disagrees with the state machine; the "trivial" task profile requires a
  transition (`ANALYZING_TASK → PLANNING`) the same state machine does not define and inputs that
  the reduced cycle never produces; the Orchestrator role and the Discovery state machine disagree
  about who computes discovery hashes.
- The repo's own state documentation is stale: `docs/VERSIONING.md` §9 says `master = 3.0.5`
  while `master` is at `3.6.3`; `docs/AUDITORIA_DOCUMENTACION.md` reports 23 RFCs in `Proposal`
  (all are now `Accepted`) and a test coupling that no longer exists; the documented verification
  battery is defined differently in three different documents, and one member of it
  (`tools/check_dist_sync.py`) is red by design on `dev`.

**Answer to the audit's primary question:** ARgentOS is *primarily an architectural/specification
framework with unresolved semantic and enforcement gaps*. It is internally disciplined and
unusually honest about its limits (fail-open hooks, agent-judgment gates), but it does not
currently deliver mechanical enforceability or operational determinism at the level its own
philosophy claims to pursue.

# 2. Architecture Map

```
User request
   │
   ▼
ArgentOS System Agent (domain system) ── health checklist + probe → SYSTEM_READY
   │
   ▼
Orchestrator (domain core) ── delegates each phase to a transient Worker
   │  ┌────────────── core state machine (18 states) ──────────────┐
   │  │ ANALYZING → CONFIRMING → SPEC → CONTEXT → VALIDATE → PLAN  │
   │  │ → EXECUTE → VERIFY → COMPLETED/ABORT, with RECOVERY loops   │
   │  └──────────────────────────────┬────────────────────────────┘
   │                                 │ gates H00–H07, H09–H11, H15 (prose policies)
   ▼                                 ▼
Harness (no runner) ── HARNESS_REPORT.md (self-authored) + state.json (3 scripts)
   │
   ▼
Discovery Orchestrator (domain discovery) ── 11 states, workers, D00/D01 gates, KB
   │
   ▼
.project/<session>/<iteration>/ artifacts  +  .project/knowledge/ (KB)
```

Dependencies (Observed): core depends on cross-cutting contracts/standards; discovery is invoked
by core but is self-contained; `protocol/.agents/` never references `plans/` (documentary
boundary); `runtime/` depends one-way on `protocol/.agents/`; `tests/` depends on neither. No
circular dependencies found in the dev tree. The only "orchestration" of the protocol at runtime
is the LLM itself.

# 5. Naming and Semantic Coherence

- **"profile" collision (Observed):** `profile:` in workflow front matter = phase role
  (`task_analyst`…); `profile` in the delegation payload = specialized profile
  (`backend_engineer`…); `intent_reflector` is simultaneously listed as a "phase role", a
  "fixed-phase profile", and a value of the payload `profile` enum
  (`protocol/.agents/roles/worker.md`, `protocol/.agents/delegation/WORKER_DELEGATION_CONTRACT.md`,
  `protocol/.agents/roles/profiles/README.md`). Mitigated by explicit disambiguation notes, but
  the token remains overloaded — a real semantic cost for implementers.
- **`produced_by` value domain (Observed):** role name (`TASK_ANALYSIS.md`: `task_analyst`),
  generic name (`INTER_WORKER_MESSAGE.md`: `discovery_workers`), states (`KB_DISCOVERY_ENTRY.md`:
  `discovery:DISCOVERY_ENV`, …), while the taxonomy uses states. The health checklist only checks
  the field's *presence* (`PROTOCOL_HEALTH.md` item 3), so no validator pins the domain.
- **"Harness" (Observed):** used for (a) the policy set, (b) the former runner ("harness runner no
  longer exists"), (c) "harness code" that D01 says may be added, (d) the state scripts. Same
  word, four referents.
- **"Runtime" (Observed):** protocol-level concept (prompt runtime), dev reference implementation
  (`runtime/`), and the adopting CLI — three uses.
- **`artifact_validated` in taxonomy for H10** is `KB_RECOMMENDATION.md` while D01/H10 documents
  describe different artifacts — consistent at the doc level, but the taxonomy's
  `artifact_validated: null` for H15 and `gates: []` shows the taxonomy models non-transition
  gates poorly.

# 7. Harness Audit

**The central finding: there is no enforcement layer. (Observed)** `harness/INDEX.md`: "The
harness is implemented as a set of policies, each carrying a «Gate Checklist» in prose that the
Orchestrator evaluates **by judgment** when the gate fires. **There is no executable validation
runner.**" Every core policy repeats "the harness runner no longer exists; every item … is
evaluated by the Orchestrator's judgment." Distinguish, per the audit rules:

- **Instruction vs enforcement:** items marked `[gate]` are "objectively verifiable structure" —
  but *who* verifies them is the Orchestrator, by judgment, with evidence it writes itself into
  `HARNESS_REPORT.md` (which only the Orchestrator may write). That is self-assessment, not a
  harness.
- **The only mechanical pieces (Observed):** `health_check.py` (writability probe),
  `runner_state.py` (records gate PASS/terminal states; runs a post-hoc mtime bypass scan),
  `hook_gate.py` (denies `PreToolUse` Write/Edit without H04 PASS, and `Stop` without iteration
  closure). The hook is **fail-open by design** ("a hook crash or timeout lets the tool call
  through") — documented honestly, but it means the *only* hard enforcement is best-effort.
- **Enforceability per gate (Observed):** H04 and H06 are partially enforced via the hook (and
  only for Write/Edit/Stop events, only when hooks are installed, only in the two documented
  CLIs). H00–H03, H05, H07, H09–H11, H15, D00, D01, S00 are prompt-level. H15's own policy
  states: "There is no executable test suite for H15."
- **Bypass paths (Observed):** the hook allows any `Bash`/`Read`/`Glob`/`Grep` call
  unrestricted; `Write|Edit` to paths whose `file_path` key is missing fail open; sessions are
  resolved by most-recently-modified fallback (concurrency-unsafe); the bypass scan is advisory
  and mtime-based.
- **Ordering/conflict (Observed):** gate ordering is defined per transition, and recovery tables
  are "first matching rule" — but the *context variables* of those tables (`artifact_exists`,
  `retry_count`, `plan_out_of_scope`, …) have no defined storage or computation; they are
  Orchestrator judgment at failure time.

**Verdict:** the harness is a documented convention with a thin mechanical shell, not an
enforceable validation system.

# 8. Policy Audit

Every policy was read (H00–H07, H09–H11, H15, D00, D01, S00, H13). Summary:

- **Declarative-only policies (Observed):** H00–H03, H05, H07, H09, H10, H11, H15, D00, D01, S00,
  H13 — effectiveness depends on the model choosing to comply.
- **Partially mechanical:** H04/H06 — state recording (`runner_state.py`) and hook deny for
  Write/Edit/Stop in enforced mode; the actual *judgment* that a gate "PASSes" is still the
  Orchestrator's.
- **Recovery tables:** all except H09/H10 have them; H09/H10 default to `RECOVERY_GENERIC`
  (documented).
- **Policy precedence:** no explicit global precedence between policies; conflicts are resolved
  by "the canonical document wins" (single-source policy) — which itself has an exception it does
  not declare (§18).
- **Determinism of evaluation (Observed):** H01's EARS item and H06's evidence-resolution items
  are checkable in principle, but the "orchestrator reads the declared value" formulation means a
  compliant agent can declare values that no mechanism validates. Example: H06 item 7 verifies
  *declared* `evidence` fields resolve — it does not verify the test ever ran (the `SESSION_LOG.md`
  "matching entry" is also self-written).
- **Declarative flags (Observed, `protocol/.agents/features.toml`):** compliance is "auditable by
  joining the active-flags entry in SESSION_LOG.md with the consumption declared in the produced
  artifacts" — both halves are agent-written; no mechanical check exists. The standard itself
  calls the absence *"unevidenced compliance"* — i.e., the system defines the gap but cannot
  detect it.

# 9. Contract Audit

All 40+ contracts were read. Classification:

- **Machine-checkable:** front-matter shape (`artifact`, `phase`, `produced_by` presence),
  required ATX headings (by agent judgment per H03/H06/H11 gate checklists), a handful of TOML
  blocks (`Final Project State`, `Steps Executed`, `Scope Compliance`, `Final Decision`,
  `Acceptance Criteria Evaluation`, `Technical Approach`, `Technical Practice Evidence`) —
  parseable in principle, but *nothing in the repo parses them*;
  `protocol/.agents/standards/runtime/PYTHON_DEPENDENCIES.md` explicitly says structured blocks
  "are parsed by the evaluating agent … not by executable validation code."
- **Textual only:** all semantic requirements ("scope is bounded", "does not invent context",
  "conflicts listed", "evidence actually supports") — contract prose.
- **Internally inconsistent contracts:**
  1. `produced_by` domain mismatch across contracts (§5).
  2. `RECOVERY_REPORT.md` allows `recommended_next_state ∈ {PLANNING, NEEDS_CLARIFICATION,
     ABORT}` — but the state machine and workflow 08 permit early-phase destinations
     (`ANALYZING_TASK`, `BUILDING_TASK_SPECIFICATION`, `GATHERING_CONTEXT`,
     `VALIDATING_CONTEXT`); a recovery report cannot legally recommend the transition the recovery
     flow actually performs. **Observed contradiction.**
  3. `WORKER_DELEGATION_CONTRACT.md` marks `recommended_next_state` deprecated "The Orchestrator
     has never consumed it" — while worker.md and various flows still reference return-report
     fields; minor drift.
  4. `DISCOVERY_MANIFEST.md` requires `role_version`, `model_used` optional, etc., while D01 item
     8 requires "the manifest lists every published entry" — no mechanical checker for any of it.
- **Completeness:** contracts define sections and completion criteria, but not
  preconditions/postconditions/invariants in a checkable form, and there is no schema version on
  contracts (migration is handled narratively in `docs/MIGRATION.md`).

**Determinism guarantee claim:** no contract contains a mechanically verifiable determinism
guarantee; the "determinism is achieved by contract, not by code" statement appears explicitly in
the Discovery Orchestrator role — an admission that determinism is normative, not enforced.

# 11. Context Audit

- **Pipeline (Observed):** Discover → Collect → Organize → Prioritize → Resolve → Compose →
  Deliver is defined as a conceptual decomposition inside `orchestrator.md` §5 and operationalized
  by `standards/context/*`. Boundaries between steps are explicit.
- **Budget (Observed):** KB budgets are 8,000/4,000 chars per phase group
  (`standards/context/CONTEXT.md` §3); materialized as estimated tokens `ceil(chars/4)` with
  2,000/1,000 defaults (`standards/context/BUDGET_MATERIALIZATION.md`). The Budget invariants
  (finite, consumable, exhaustible, representation-independent) are **declared, not enforced**:
  `context_budget` in the payload is a ceiling; nothing measures or enforces consumption. The
  metrics model records `declared` vs `consumed` — but those are agent-recorded events.
- **Determinism (Observed):** every Resolution policy (`RESOLUTION_TIE_BREAKING`,
  `RESOLUTION_DEDUPLICATION`, `RESOLUTION_MERGE`, `RESOLUTION_UNRESOLVABLE_CONFLICTS`) and both
  Composition policies explicitly mark all criteria `[agent]` and defer deterministic checks to
  "harness Future Extension". Tie-breaking has an ordered criterion list (explicit directive →
  source precedence → recency → coverage → first-fit), which is deterministic *in form*, but each
  criterion's evaluation is judgment.
- **Known nondeterminism points (Observed):** candidate discovery source selection, relevance
  assessment, containment judgment (dedup), mergeability judgment, compression decisions, the 10%
  inline-vs-reference threshold (agent-measured), "representative names" sampling in discovery
  workers, and KB budget splitting (`budget/N` with a 500-char floor is arithmetic, but selection
  is judgment).
- **Ordering:** payload priority order is defined (`CONTEXT.md` §1); context ordering effects are
  acknowledged as impactful but not machine-verified.

# 12. Determinism Audit

Per the audit's categories:

| Type | Verdict (Observed) | Mechanism |
|---|---|---|
| Computational determinism | Not established | No executable runtime; the only deterministic code is the 3 scripts + dev checkers |
| Procedural determinism | Partial | State machine + gates are defined; but trivial-profile transition is undefined, RECOVERY destinations conflict (taxonomy), and gate PASS depends on judgment |
| Context determinism | Not guaranteed | All resolution/composition rules `[agent]`; "Future Extensions" deferred |
| Policy determinism | Not guaranteed | Recovery tables are ordered, but their context variables are unspecified; two policies (taxonomy vs state machine) conflict on RECOVERY |
| Execution determinism | Partial | state.json transactional writes + hooks are deterministic; hook fail-open, mtime-based bypass scan, most-recent-session fallback, CLI differences are uncontrolled |
| Semantic determinism | **Weak** | Multiple valid interpretations exist (see Final Question) |

**Controlled vs uncontrolled sources (Observed):** model choice/temperature/provider are outside
the protocol (no declaration in the payload; `DISCOVERY_MANIFEST` has optional `model_used`);
filesystem ordering matters for the hook's session fallback and the bypass scan; timestamps are
UTC ISO-8601 where specified but session/artifact timestamps are agent-written; retry semantics
(1s/2s/4s backoff, max 3) are declared for discovery workers but core-gate retry bounds are "by
default one retry" (reviewer) or `retry_count` (unspecified persistence); the KB freshness checks
depend on TTLs from `features.toml` and agent-read timestamps.

# 13. Zero-Hallucination Audit

Decomposed (Observed):

- **Prevention:** prompt-level rules (`ANTI_CIRCUMVENTION.md`, `NO_ASSUMPTIONS.md`, no-assumption
  interaction mode, intent reflection, `CONFIDENCE.md` anti-inflation rule). None are mechanical.
- **Detection:** `hallucination-checker` skill (a prompt procedure), D01 "ground truth" items
  (all `[agent]`), H06 evidence resolution (`[gate]`-style but reads declared fields),
  verification report self-checks. No deterministic hallucination detector exists anywhere in the
  payload or tooling.
- **Containment:** artifacts are kept in `.project/`; `.agents/` immutability; the bypass scan
  (mtime-based) is the only post-hoc mechanical detection of out-of-plan writes — it is advisory
  and only runs when H04 is recorded.
- **Correction/recovery:** recovery loop + retroactive-artifact marking; judgment-based.
- **Observability:** `HARNESS_REPORT.md`/`SESSION_LOG.md` are self-authored; `METRICS.md` event
  comments are agent-written JSON in HTML comments that nothing validates.

**Verdict:** the only defensible claim today is *"hallucination is normatively prohibited and
post-hoc auditable in self-reported traces."* Any stronger claim ("zero hallucinations", "ground
truth guaranteed") is aspirational: **no mechanism prevents an LLM from violating the
requirements; the protocol's answer everywhere is the prompt telling it not to.** D01's

# 15. Failure and Recovery

Defined failure paths (Observed): per-gate Recovery Decision Tables (first-match), generic
`RECOVERY_GENERIC`, `NEEDS_CLARIFICATION`, `ABORT` (founded abort: `RECOVERY_REPORT` +
`SESSION_LOG`), discovery `DISCOVERY_FAILED` with KB-criticality routing (D4), bootstrap
`BOOTSTRAP_FAILED` with the single user-authorization exception, worker retry-once rules,
discovery worker 3-retry/backoff.

Undefined/unsafe paths (Observed):

- **Gate failure with no table:** H09/H10 → documented generic fallback; OK but the generic
  fallback has no decision criteria ("Orchestrator applies 08-recovery.md").
- **`retry_count` provenance:** recovery tables condition on it, but nothing specifies where it is
  stored/read from (implied: HARNESS_REPORT entries read by judgment).
- **Hook failure:** fail-open (documented); bypass scan compensates only for H04-time writes; a
  hook *timeout* during execution is invisible post-hoc.
- **Corrupt/absent `state.json`:** fail-closed for consumers (documented, tested).
- **Session resume after crash:** reconstruction from log/brief is judgment-based; partial-
  iteration "last intact artifact" has no mechanical definition of "intact".
- **Concurrent sessions:** the hook assumes a single active session (mtime fallback); no locking.
  Two agents in one project can cross-gate each other's iterations.
- **Discovery partial degradation:** "continue without that output (partial degradation)" is
  allowed for workers, but which outputs are safely omittable is not specified (only `init_worker`
  is marked critical).
- **LLM malformed output:** handled as gate failures (format branch), bounded retries; but the
  *detection* of malformedness is judgment.

# 16. Testability and Verification

What is mechanically testable today (Observed): reference resolution, payload boundary,
taxonomy-metadata presence, skills inventory/front-matter, plan citations/structure, `dist` sync,
state.json scripts + hooks (product tests), runtime materializations (dev tests, fixture-based).

Claims with **no falsifying test** (Observed):

- "Gates enforce the workflow" — no test can fail, because there is no enforcement to test (only
  hook scenarios).
- Taxonomy/state-machine coherence (H13) — explicitly untested; the former
  `test_protocol_taxonomy.py` was removed.
- Context budget respect, resolution/composition determinism — untestable as specified; policies
  call them "Future Extensions".
- Zero-hallucination / ground-truth guarantees — untestable; D01 is judgment.
- Declarative-flag compliance — "unevidenced compliance" is defined but undetectable.
- Versioning invariant (version ↔ changelog ↔ tag) — no checker; currently violated in
  *documentation* (`docs/VERSIONING.md` §9) and structurally unverifiable on `dev` (`VERSION`
  3.8.0 has no tag by design).
- Metrics correctness — `ENTRY`/`METRIC` JSON comments are not schema-validated anywhere.

Also (Observed): the **product harness tests are excluded from the repo battery by design**
(`tests/AGENTS.md`: "Harness tests are not run here"), so a change that breaks
`hook_gate.py`/`runner_state.py` is not caught by CI in this repo — the very gap
`docs/AUDITORIA_DOCUMENTACION.md` flags, which plan 46 mitigated only by shipping the tests.

# 17. Hidden Assumptions

- Single active session per project; session UUIDs are unique; the CLI session id is not the
  protocol session uuid (hook fallback).
- Hook event schema matches Kimi/Claude (`session_id`, `hook_event_name`, `tool_name`,
  `tool_input` with `file_path|path|filename`) — no schema contract in the payload.
- Filesystem mtimes are reliable for bypass detection (the repo itself discarded a clock-drift
  finding, F-10, as noise).
- `python` is on PATH and Python ≥3.11 with stdlib is available in enforced mode.
- The CLI supports blocking hooks (only Kimi Code and Claude Code are documented).
- Model compliance with every MUST; models are capable of EARS, TOML, JSON, and CAVEMAN fidelity.
- Artifact headings match contracts exactly (case-insensitive) — the basis of all "structural"
  checks.
- Timestamps are UTC ISO-8601; the agent writes them correctly and never rewrites history.
- KB character budgets approximate model context meaningfully; `chars/4` is a valid token estimate
  for the adopting model.
- The environment and project are stable within TTL windows (24h/6h).
- `dist` exists locally for `check_dist_sync`; CI never runs it.
- No user edits `.project/` or bypasses hooks out-of-session (documented as an accepted limit).
- UUIDs and iteration numbers start at 00 and increment by 1.
- Two domains never share the `<order>` sequence space, and artifacts never collide.

# 18. Contradictions

1. **Taxonomy vs state machine (RECOVERY).** `PROTOCOL_TAXONOMY.md` `core:RECOVERY.next =

   transitions allowed by the taxonomy) is therefore violated by the payload itself.
2. **Trivial profile vs state machine.** `ANALYZING_TASK → PLANNING` is used by the trivial path
   but defined nowhere; workflow 05 requires `CONTEXT_READY` + three artifacts the trivial cycle
   never produces; `EXECUTION_PLAN.md` must reference `TASK_SPECIFICATION.md`, which trivial tasks
   do not create.
3. **Hash actor.** `orchestrator.md` §4.3 (Orchestrator computes hashes and sends them in the
   invocation payload) vs `DISCOVERY_STATE_MACHINE.md` §Hash Calculation ("never computes hashes
   itself"; `init_worker` computes). Plan 53 (`e88d416`) was titled "single hash actor" and
   changed only the discovery side.
4. **Versioning state.** `docs/VERSIONING.md` §9 (`master`/`dev` = 3.0.5) vs `master` 3.6.3,
   `dev` 3.8.0, tags ≤ 3.6.3, `dist` 3.6.3.
5. **Documented state of the repo.** `docs/AUDITORIA_DOCUMENTACION.md` (23 RFCs in Proposal;
   `test_toolcalls` coupled; 114 tests) vs actual (all Accepted; fixture-based; 121 passed).
   `plans/INDEX.md` header likewise.
6. **Single-source policy vs its own payload.** `PROTOCOL_BOUNDARIES.md` says rules MUST be
   defined in exactly one canonical file and other files MUST NOT duplicate full content;
   `ANTI_CIRCUMVENTION.md` contains a full inline immutability rule (deliberate, plan 56 — an
   exception the policy text does not declare).
7. **Battery definition.** Three different definitions of "the battery": `AGENTS.md`
   (invariants, citations, structure, dist-sync, pytest), `docs/VERSIONING.md` §4 (invariants,
   citations, structure, H13-by-judgment, tests — no dist-sync), `plans/INDEX.md` §Convenciones
   (invariants + health_check + citations + structure + dist-sync + pytest). And `check_dist_sync`
   is red on `dev` by construction, so "battery green" is only attainable on `master`.
8. **Changelog order/aging.** `[3.8.0]` (2026-08-14) sits above `[Unreleased]`, which holds

10. **`RECOVERY_REPORT.md` enum** excludes the early-phase recommendations the recovery flow

11. **D01's "Implementation Note"** ("the harness is not an instruction for the agent" / may
    contain Python) vs the rest of the payload ("There is no executable validation runner",
    harness = "a set of validation policies … evaluated by judgment"). A future implementer must
    decide which model is true.
12. **`DISCOVERY_MANIFEST.md` name vs `.discovery_manifest` path**, and `INTER_WORKER_MESSAGE`
    `produced_by = "discovery_workers"` vs taxonomy `produced_by: [discovery:DISCOVERY_INIT]`.

# 20. Critical Findings

**Finding: F1 — The "harness" is self-assessment, not enforcement.**

- Classification: Enforcement Debt / Hallucination-Control Debt
- Severity: Critical
- Evidence: `protocol/.agents/harness/INDEX.md` ("There is no executable validation runner…
  evaluated by judgment"); every H-policy "Evaluation audience" note; `HARNESS_REPORT.md` contract
  ("written by the Orchestrator… no other agent edits it"); `runner_state.py` docstring ("the
  Orchestrator judges each gate in prose and this script only RECORDS the outcome").
- Problem: the auditor and the audited are the same agent; the "audit trail" records the agent's
  own declarations.
- Why it matters: every claim of "validated", "enforced", or "reproducible" downstream of the
  gates rests on model compliance.
- Determinism impact: gates can pass/fail differently across runs with identical inputs.
- Hallucination-control impact: nothing prevents the orchestrator from declaring PASS on invalid
  artifacts.
- Confidence: High

**Finding: F2 — The trivial task profile is internally incoherent.**

- Classification: Contradictory / Unimplemented
- Severity: Critical
- Evidence: `AGENT_STATE_MACHINE.md` §Task Profiles ("path is ANALYZING_TASK → PLANNING →
  EXECUTING → VERIFYING") vs §ANALYZING_TASK allowed transitions (no PLANNING) and workflow
  `05-plan.md` (requires `CONTEXT_READY` and TASK_SPECIFICATION/CONTEXT_ARTIFACT/
  CONTEXT_VALIDATION_REPORT inputs).
- Problem: the reduced cycle uses an undefined transition and consumes artifacts it never
  produces; `EXECUTION_PLAN.md` (mandatory for trivial) references a spec that does not exist.
- Why it matters: the protocol's own "reduce work" mechanism cannot be implemented
  deterministically.
- Determinism impact: two compliant implementations would diverge immediately on any trivial
  task.
- Confidence: High

**Finding: F3 — Multiple authoritative sources disagree on RECOVERY.**

- Classification: Contradictory / Source-of-truth conflict
- Severity: Critical
- Evidence: taxonomy `core:RECOVERY.next` vs state machine RECOVERY section vs workflow 08 front
  matter vs H03 recovery table.
- Problem: the "single master dictionary" is contradicted by the documents it governs, and the
  mechanical battery cannot see it.
- Determinism impact: undefined next-state selection in the most failure-heavy part of the flow.
- Confidence: High

**Finding: F4 — Zero-hallucination and ground-truth guarantees are aspirational.**

- Classification: Unverifiable / Hallucination-Control Debt
- Severity: Critical
- Evidence: D01 all items `[agent]`; H06 test-evidence check reads declared fields;
  `hallucination-checker` is a prompt skill; `ANTI_CIRCUMVENTION` is conduct prose.
- Problem: no deterministic validator exists for the system's central epistemic claim.
- Determinism impact: correctness depends entirely on the model.
- Hallucination-control impact: detection, containment, and correction are all judgment-based.
- Confidence: High

**Finding: F5 — Context determinism is explicitly deferred.**

- Classification: Determinism Debt / Specification Debt
- Severity: High
- Evidence: `RESOLUTION_*.md`, `COMPOSITION_*.md` mark every rule `[agent]` and name
  deterministic checks "harness Future Extension"; `BUDGET_MATERIALIZATION.md` defines the unit
  but nothing enforces the budget.
- Problem: the Context system is the most elaborate part of the model and the least
  machine-checkable.
- Confidence: High

**Finding: F6 — Repo state documentation is stale and the battery is undefined.**

- Classification: Documentation Debt / Validation Debt
- Severity: High
- Evidence: `docs/VERSIONING.md` §9 (3.0.5) vs git (`3.6.3`/`3.8.0`);
  `docs/AUDITORIA_DOCUMENTACION.md` (23 Proposal RFCs, coupled tests, 114 tests) vs actual; three
  battery definitions; `check_dist_sync` red on dev.
- Confidence: High

**Finding: F7 — Declarative flag compliance is undetectable by design.**

- Classification: Enforcement Debt
- Severity: High
- Evidence: `features.toml` header + `standards/INDEX.md` §Flag categories: compliance is a
  two-part join of self-written SESSION_LOG entries and self-written artifact declarations;
  "unevidenced compliance" is defined but not detectable.
- Confidence: High

# 22. Architectural Risk

If the current architecture evolves without addressing the above: the payload grows faster than
its verification; every new policy adds prose "checklists" that nothing enforces, so the
*apparent* guarantee surface grows while the *actual* guarantee surface stays at three scripts;
contradictions like RECOVERY/trivial/hash accumulate unnoticed because the only coherence
validator is the LLM itself; the governance apparatus (already flagged internally as "escala peor
que el protocolo") keeps regularizing its own drift; adopting teams — the actual consumers — will
hit semantic divergence between what the docs promise and what any concrete runtime does, and the
trust the protocol builds through its excellent bookkeeping will be spent on unverifiable claims.
The 10× growth scenario: reference resolution and skills checks scale fine; judgment-based
coherence does not — it degrades linearly with the number of cross-referenced documents.

# Final Question

> **If a completely independent engineering team received the current ARgentOS repository and
> attempted to implement a compatible runtime solely from its specifications, how many important
> decisions would they still have to make themselves?**

**Qualitatively: a large number, concentrated in semantic territory.** The mechanical skeleton
(files, references, front matter, state.json, hooks) is unambiguous; the decision space is
everything semantic:

1. **Gate evaluation:** how to judge each `[agent]` checklist item, what counts as evidence, how
   to score EARS criteria, what "verifiable" means per criterion — the policies enumerate items
   but not a decision procedure.
2. **Context system:** candidate discovery, relevance, containment/merge judgment, budget
   accounting and truncation — every policy says "agent judgment, Future Extension".
3. **Discovery:** sampling ("representative names"), ground-truth validation, merge conflict
   resolution, per-worker criticality for partial degradation.
4. **Delegation/routing:** H15 evaluation, profile selection edge cases (the 7 questions have a
   tie-splitting procedure but the *frontier* check is judgment), skill override justification.
5. **Recovery:** populating recovery-table variables, choosing among overlapping destinations,
   retry bookkeeping.
6. **Contradiction resolution:** they must silently pick a side on RECOVERY transitions, the
   trivial path, and hash computation — or ask the authors.
7. **Session resume/iteration semantics:** "last intact artifact" and reconstruction from logs.
8. **Versioning/operability:** what "battery green" means, how to treat `dev`-vs-`dist`
   divergence, how to handle the stale state docs.
9. **Metrics/observability:** aggregation procedure is described narratively; event schema is
   not validated.

> **Could two competent independent teams implement ARgentOS differently while both reasonably
> believing they followed the current specification correctly?**

**Yes — in specific, enumerable areas.** The concrete divergence points: (a) trivial-profile flow
(undefined transition + missing inputs), (b) RECOVERY routing (taxonomy vs state machine vs
recovery-report enum), (c) hash computation actor and payload contents, (d) gate PASS thresholds
for every `[agent]` item (especially EARS conformity, scope compliance, test evidence), (e)
context composition/resolution outcomes and budget enforcement, (f) discovery
sampling/merge/ground-truth judgments, (g) session resume and retry bookkeeping, (h) whether
D01/H15 are ever implemented as code. In each, both teams could cite the same documents and
produce different, mutually incompatible runtimes. **This is the strongest indicator that
ARgentOS's semantic determinism today is a goal, not a property.**
